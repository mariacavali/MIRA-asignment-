# MIRA System Brief for Peer Audit

MIRA is a private, authenticated web application for brand recognition and creative direction. It is intended for an individual founder, creator, or consultant developing a personal or organisational brand world. The current repository contains two active, data-isolated product surfaces: MIRA V3, a recognition and confirmed-deliverables journey available at `/` and `/mira-v3`; and MIRA V4, the Project 3 creative-direction journey available at `/mira-v4`. A newer `/mira-1` level-based extension is also present but is only partially productized.

In V4, the user supplies quick context about what they are building, the audience, intended feeling, and moodboard purpose; private birth details; short recognition and creative-discovery answers; a structured creative brief; and, optionally, one inspiration image with an explanation. The server stores journey state and messages in owner-scoped MySQL/TiDB tables managed through Drizzle. An authenticated tRPC API mediates reads and mutations.

MIRA uses Forge-backed chat completions, with `gpt-5-mini` identified in the current V4 services, to generate bounded adaptive questions and synthesize a structured, versioned Creative DNA record. A deterministic Campaign Compiler turns validated Creative DNA into a five-scene campaign plan. The server then uses a TypeScript Maria visual-direction layer and Forge ImageService (`MODEL_GPT_IMAGE_2`) to create initial visual directions, one refinement round, and a final five-image editorial moodboard. Generated assets and uploaded images use Forge presigning and S3-backed object storage. The user selects directions and supplies preserve/avoid instructions; generated results are cached and tied to the authenticated owner.

V3 remains implemented as a separate recognition journey using conversation, an editable and confirmable Mirror, optional consent-gated reference images, and confirmation-gated PDF deliverables. Its optional Dakidarts numerology adapter is server-side and feature-gated. There is no active Human Design provider in the available implementation. V3 data does not automatically transfer into V4.

The application was verified in private staging rather than as a public deployment. Existing evidence records one completed authenticated V4 five-image moodboard run and a completed V3 journey. Later live image generation was limited by external provider usage availability. Production hosting, current processor regions, retention periods, and the final operating organisation are not confirmed from the available implementation.
